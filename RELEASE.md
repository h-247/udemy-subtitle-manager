The authoritative hosted source is `chatgpt-sites/udemy-subtitle-manager` in this repository. `sites/udemy-subtitle-manager` is an ignored Sites Git checkout used only to publish a tested snapshot. Do not develop independently in that checkout. The Python backend and `frontend` remain the supported local application.

1. Commit intended changes, including Drizzle migrations and regression tests. Push to GitHub and wait for **Release checks** for that exact commit. CI runs backend tests, Sites regression tests and the production build. Use Node 24 and Python 3.11.
2. From the clean root run `node scripts/prepare-sites-release.mjs`. It rejects uncommitted work or a commit without successful GitHub checks, copies the canonical source and writes deployment provenance. Open the existing Sites project with the Sites source helper before preparing the snapshot, to reconcile the remote first.
3. Run the Sites source helper against the deployment checkout with the existing project ID, fresh source credential on stdin, the production build command, and an archive path. The helper pushes the exact deployment source and packages its build. Save and deploy that returned commit/archive while preserving owner-only access. Deploy applies the committed Drizzle migrations.
4. Verify `/api/health` reports the root commit, invoke the protected dispatcher, and read back job/subtitle state on the hosted app. Record root commit, Sites source commit, version, deployment ID, URL, and verification results in a GitHub release. Deployment success alone does not prove browser-close/restart recovery against Udemy and Drive.

`Hosted job dispatcher` runs every five minutes and can also be dispatched manually. GitHub scheduling may be delayed; it is not a latency guarantee. Store `SITE_SERVICE_TOKEN` (the existing Site service access token) and `JOB_RUNNER_SECRET` in GitHub Actions secrets, with the same runner secret in Sites production environment. The service token passes the private Site access gate; the independent runner secret authorizes only job advancement. Never put tokens into tracked source, command arguments, release records, or logs.

The dispatcher makes bounded requests until idle or four minutes have elapsed. Requests and dashboard closure do not own progress. D1 stores a per-user exclusive ten-minute lease, resumable import payload/batch cursor, retry count and next retry time. A process restart releases nothing prematurely: a crashed lease expires, then another invocation resumes. Network calls have twelve-second deadlines. Failures retry with exponential backoff up to eight consecutive attempts, then retain their checkpoint for explicit **Retry job**. Cancellation stops subsequent steps; an in-flight item may finish.

Caption selection uses the requested base language (`en`); `caption_language` retains the actual locale (`en_US`). Migration 0002 keeps the best durable row for each lecture/base language and removes superseded bookkeeping failures without deleting R2 or Drive files. Regional variants intentionally share the existing base-language selection semantics. Download `status` and `drive_status` are separate. A Drive retry reads the stored R2 caption and uses a reserved Drive ID persisted before upload, so remote success followed by a lost database write can be reconciled without a duplicate file.

New imports accept optional tags in the URL form. After curriculum import, one D1 transaction saves those tags and transitions the same durable job to a video-only subtitle batch. A restart cannot enqueue a duplicate batch. Existing-course tag editing is removed; tags remain visible and filterable. Curriculum re-sync preserves existing tags and does not start a separate download batch.

Subtitle execution starts immediately after authenticated enqueue/retry/resume POSTs via the Worker execution context (`waitUntil`), with a bounded drain and the same D1 lease/checkpoints. Dashboard job reads send a separate resume POST for pending work; GET endpoints remain read-only. GitHub dispatch remains the unattended recovery path. Caption 401/403/404 refreshes metadata once using the remote Udemy course ID before retrying the signed URL; CDN fetches never include Udemy session credentials.
